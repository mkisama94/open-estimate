## 2. 機能と保存場所

| 担当 | 主な機能 | 保存・参照する情報 |
| --- | --- | --- |
| Work／CodexのSkill・会話 | 読み取り対象の確認、意味の解釈、質問、結果説明、発行・公開の意思確認 | 会話の扱いはホストと利用するモデル提供元の設定・契約に従う。 |
| ローカル実行部 | ホスト標準ツールと補助スクリプトによる許可範囲内の読み取り、測定時点の固定、根拠参照の整合検査。ローカルMCPは不要 | ソース、ローカルの測定根拠、未送信の評価、必要な処理再開情報。サーバーから見ればクライアント申告。 |
| Open EstimateリモートMCP・API・DB | 受領データの検証・再計算、表示時FRB換算。証明書発行、管理対象と権限の関連付け、公開状態の更新は各契約確定後に実装 | 利用者が保存・発行に同意した構造化評価、証明書、管理権限、公開状態、操作記録。 |
| 所有者向けWeb | 保存済み評価・証明書の一覧、状態確認、対象と影響を明示した管理操作 | サーバーの管理記録を参照する。ブラウザ内の保存だけを正本にしない。 |
| 公開Web | 公開要約、証明書、検証結果の表示 | 公開許可リストに含まれ、公開が確定した情報だけ。 |

「Webで継続管理する」ことは、未確定の会話やローカルの下書きを無条件に同期することではない。試算中の評価を保存する場合にも、保存される項目を示して同意を得る。未送信の評価が別端末でも復元できるとは約束しない。

Webに管理情報を集約しても、プラグインと管理対象を関連付ける認証情報や、通信中断後の照会に使う最小限のローカル記録は必要になり得る。その方式は認証設計で定める。ローカルの管理キーを紛失すると唯一の管理手段を失う、という従来案を前提にしない。

## 3. ソースと評価データの境界

### 3.1 Open Estimateへの送信・保存

- ソースファイル、圧縮リポジトリ、コードの抜粋、コードが写った画像は、Open Estimateへの送信項目に含めない。
- 発行・保存に必要な構造化評価、使用した基準・設定、同意した内容を送る。送信項目はAPIの許可リストで定める。
- 機能名、説明、相対パス、行番号なども機密情報を含み得る。コード本文とは別に、保存する必要性と開示範囲を定め、送信前に確認できるようにする。現時点では全項目の送信を承認済みとは扱わない。
- AIが説明欄へコードを貼り付ける経路を設けない。Skillの指示だけでなく、入力形式・長さ制限・内容確認・実際の送信検査を組み合わせる。単に文字列型のSchemaを定義しただけでは「コードを送らない」の保証にならない。
- 公開内容には、ソース・非公開の測定根拠・パスを含めない。公開する見積値や説明も、公開用の許可リストと利用者の確認を経由する。
- アクセスログ、エラー記録、解析サービスへの記録にも同じ境界を適用する。

ソース本文を受領しない以上、サーバーによる検証は受領した構造化評価の形式・整合性・再計算などが対象となる。署名を「サーバーがソースの内容やAIの解釈の正しさを確認した証明」と説明しない。

### 3.2 Codexとモデル提供元への送信

ローカル実行は、完全なオフライン推論を意味しない。Codexが読み取ったコードやツールの結果は、AI処理の入力としてモデル提供元に送られる場合がある。これはOpen Estimateの発行・管理APIへの送信と別の経路である。

OpenAIの公式説明も、ローカルファイルが端末に残る場合でも、処理に必要なファイルの抜粋やツール結果などがOpenAIのサービスへ送られる可能性を明記している。契約、設定、利用するモデルによる扱いを、Open Estimate独自の保証として上書きしない。

参照：[Local execution security](https://learn.chatgpt.com/docs/enterprise/chatgpt-work-local-security)（2026-10-11確認）。

したがって「ソースコードはネットへ一切送信されない」「端末から絶対に出ない」「完全オフライン」という表現は採用しない。ネットワークへの送信そのものを禁止する要件に変更する場合は、推論環境から設計し直す必要がある。

## 4. 繰り返し伝える製品コピー

以下は目標とする実装を説明する文案であり、現行実装に対する検証済みの広告表現ではない。対応する受入試験を満たしたうえで使用する。

主表示：

> ソースコードはOpen Estimateのサーバーへアップロードされず、一般公開もされません。

近接する補足：

> Codexは、AIによる解析のためにコードをモデル提供元へ送信する場合があります。Open Estimateへ保存する評価情報と、一般公開する内容は、確定前に確認できます。

初回のコード読み取り前には、主表示と補足を一緒に示す。利用者が重要な操作を行う場所では短い説明を再掲し、詳細をすぐ確認できるようにする。強い主表示だけを見せ、送信に関する補足を見つけにくい場所へ隠さない。

| 接点 | 表示する内容 |
| --- | --- |
| 紹介・導入案内 | 主表示と、CodexのAI処理を区別する説明。 |
| 初回測定の開始前 | 対象プロジェクト、読み取り範囲、主表示と補足。 |
| 測定結果 | コード本文をOpen Estimateへ送らず評価したこと、まだ保存・発行・公開していない場合はその状態。 |
| 保存・発行の確認 | 主表示、実際に送る評価項目、保存先、保存期間・削除の扱い。 |
| 初回公開の確認 | 第三者に見える内容のプレビュー、コード・非公開根拠を含めないこと。 |
| Webの管理画面 | 評価情報と公開情報の区別、ソース本文を保管していないこと。 |
| 公開詳細・証明書 | ソースを公開していないこと、検証できる範囲と証明の限界。 |

繰り返し説明することと、同じ承認を繰り返し要求することは分ける。会話で有効に確定した初回公開を、Webでも同じ内容で再承認させる設計にはしない。

## 5. 会話での確定とWeb管理

確定事項は、初回の測定・発行・公開を会話で進め、継続管理をWebに設けることである。個別操作の配置は、次を詳細設計の初期案とする。

| 操作 | 配置案・動作 |
| --- | --- |
| 新規測定・再測定 | Work／Codexのローカル実行環境で、Skillと標準ツール・補助スクリプトを使う。 |
| 証明書の初回発行 | 送信内容を説明し、会話で意思確認して発行する。 |
| 初回公開 | 公開プレビューを提示し、その内容に対する会話上の承認で公開する。 |
| 保存済み評価・証明書・公開状態の確認 | Web管理画面で一覧と詳細を確認する。 |
| 公開の取り下げ・管理権限の変更など | 対象と影響を固定して確認できるWeb管理画面を主な操作場所とする。 |
| 会話からの管理依頼 | 対象を特定して該当する管理画面へ案内する。リンクを開いただけでは状態を変更しない。 |
| 署名済み内容の変更 | 既存の署名済み内容を上書きせず、新しい評価・証明書との関係を記録する。 |

取り下げ等をMCPからも直接実行可能にするか、Webに限定するかは、操作一覧の確定時に決める。Web管理の追加だけを理由に、すべての状態変更を一律に会話から禁止・許可しない。

所有者向けWebには、Google認証とメール認証による登録・ログイン機能を設ける。保存済み評価・証明書・公開状態の管理権限は、Open Estimateの内部利用者IDに結び付ける。ChatGPT認証は将来の追加候補とし、初期開発には含めない。

プラグインとWebの連携は、次を詳細設計の基準とする。

1. サーバーへの保存・発行に進む前に、Webで登録・ログインし、プラグインとの連携を確認する。
2. 連携後の保存・発行は、認証された内部利用者IDを所有者として記録する。ログインや連携だけで、保存・発行・公開に同意したことにはしない。
3. 初回の発行・公開の内容は、引き続きCodexの会話で確定する。
4. Webにログインすると、自分に管理権限のある記録を確認・操作できる。端末変更後も同じアカウントで管理を継続する。

メール認証の具体方式（確認コード、ログインリンク、パスワード等）、認証基盤、プラグイン連携の手順・期限・解除、アカウント復旧は詳細設計で定める。同じメールアドレスを持つGoogle認証とメール認証の統合は、本人確認済みの連携手順を定め、文字列の一致だけで自動統合しない。認証情報を公開URLや会話に露出する設計にしない。

## 7. 詳細実装前に揃える契約

1. **Work／Codexでの配布・実行**：ローカルMCPを必要としないプラグインの構成、Skill・補助スクリプト、ローカル実行環境、プロジェクトの選択方法、対応環境、導入確認手順。
2. **Web管理と権限**：Google認証・メール認証によるWeb登録を前提に、メール認証の具体方式、認証基盤、プラグインとの関連付け、アカウント連携・復旧を定義する。ローカルの試算と、ログインが必要な保存・発行後の管理を分ける。
3. **共通データ契約**：評価ID・証明書ID・公開ID、Schemaの版、状態遷移、同意と対象データの結び付け、APIの入出力、エラー形式。
4. **操作と再開**：会話とWebの操作一覧、二重実行防止、通信切断後の照会・再開、競合時の扱い。公開取り下げと証明書失効を混同しない。
5. **送信・保存・公開の項目**：各データの許可リスト、保持期間、削除可能な情報、検証のため保持する履歴。実際の送信確認画面と説明文まで定める。

ローカルの計数・検証や会話フローの整理は進められる。一方、これらの契約が揃う前に、認証方式や公開APIを旧仕様のまま固定しない。

N03は既知の漏えい経路を検査する試験であり、一つの試験の成功だけで、あらゆる入力に対する非送信を実証したとは扱わない。
