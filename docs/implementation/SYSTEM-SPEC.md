# Open Estimate システム仕様

更新日：2026-10-28。状態：目標仕様。現行0.10.0の実装・本番受入完了を意味しない。

## 1. 目的と優先順位

中核成果物は、利用者が手元で保持できる証明付き見積文書である。Web掲載・アカウント保存を完成の条件にしない。本書は構成、責務、標準フロー、認証・保存の境界について従来文書に優先する。残存する旧実装・受入・運用文書は現行コードの参考記録であり、本書と矛盾する前提を新規実装へ持ち込まない。

## 2. 責務

| 処理系 | 担当 | 要求しないもの |
|---|---|---|
| リモートMCP | 版付き測定・計算ルール、数値検証、証明発行 | Web表示、本人用見積保存、ブラウザーセッション |
| ChatGPTローカル | 対話、範囲確認、ソース取得・解析、算定、Markdown・UI・PDF、送信同意 | 発行元の署名鍵、WebのDB・内部状態 |
| Web表示 | MarkdownのPOST受信、安全なHTML整形、添付証明の検証 | 再解析・再計算、OAuth、保存DB、元run |
| 任意の保存機能 | 本人確認、保存、履歴、期限、延長・削除 | 基本の算定・証明・表示の前提になること |

ローカル表示用MCPはローカル側の接続手段。リポジトリやサービス数を増やすこと自体を目的にしない。共有する純粋なデータ型・表示部品は許容し、実行時の状態・DB・配備条件の共有を避ける。

## 3. 標準フロー

対象確認 → ローカル解析・算定 → 結果確定・Markdown・UI・PDF → 同意後にMCP検証・証明取得 → 希望時にWeb表示。

開始時に全体像と提供状態を示す。ソースはOpen Estimateへ送らない。AI解析ではモデル提供元（OpenAI、Anthropicなど、利用中のAIサービスのモデル提供元のこと）で処理される場合があることを説明する。

本文解析前に範囲同意を得る。計測対象・補助資料・取得対象外を実際の取得に反映する。本文取得前に容量・件数・除外衝突を確認し、主要ソース不足時は解析前に調整する。名前だけで機能実装を除外しない。上限超過は無断の範囲縮小でなく分割取得等で対応し、欠落・二重計上・途中変更を管理する。

正式なルール版を固定して算定する。数値計算とAIの説明生成を分離する。Webの接続・保存設定を解析開始条件にしない。新規ルール取得の失敗と、確定済み文書の表示を区別する。

## 4. 成果物と契約

標準文書はMarkdown。総工数の中央値、人日、参考幅、対象範囲の説明、測定日、全体／部分、機能規模、参考金額・為替条件、ルール・係数版、暫定判断・未確認事項、TEST区分、証明範囲を含む。

外部へ渡す標準文書にはソース、秘密情報、詳細なローカルパス、根拠本文、判断台帳を含めない。これらはローカルの別成果物に保持する。

検証依頼はルール版、数値モデル・結果・条件、品質・取得充足情報、確定文書、操作IDからなる。主要数値欄は標準形式とし、MCPが構造化結果との一致を検査できること。自由記述の意味判断は検証対象外。

証明データは文書と別に保持可能とする。証明番号、発行元・日時、方式版、対象文書ハッシュと方式、ルール版、検証種類・結果・範囲・制約、鍵識別子、電子署名を含む。番号だけを真正性の根拠にしない。

ハッシュ対象の文字コード・改行等を固定し、HTML変換前に検証する。署名後の本文変更は新しい版として扱う。ルール契約・検証契約・証明契約・表示契約を独立して版管理する。相手の内部URL形式、DBキー、受付状態を契約に持ち込まない。

## 5. MCPの検証と証明

同じ版のルールを変更しない。未知・非対応・停止版を明示し、最新版へ暗黙置換しない。

入力形式、ルール版、数値モデル、算術、文書の主要数値との一致を検査し、成功時だけ対応する証明を発行する。文書登録のみと数値検証済みを区別する。

証明は、指定ルールとの数値整合・対象文書との対応・発行元署名を対象とする。ソースの網羅性、AIの意味解釈、実工数・納期・市場価格、匿名提出者の本人性は保証しない。

同じ操作ID・同じ内容の再送は同じ結果を返す。異なる内容の同じIDは拒否する。再送・照会に必要な最小発行記録は保持できるが、利用者向け保存と分離する。保存項目・期間を運用仕様に明示し、本文永続保存を必須にしない。署名鍵・検証鍵の信頼管理、入力上限・濫用防止は維持する。

## 6. ローカル表示・PDF・同意

総工数の中央値を先頭で大きく示し、人日・幅・品質、対象・日付、金額・規模・内訳、根拠・条件の順に表示する。主要ソース不足なら「全体工数：未算出」を主表示し、部分試算を総工数としない。

Intelligent UIで詳細・PDF・証明取得・Web表示を操作できること。非対応時は本文・ファイル・標準確認へ代替し、実UI受入と混同しない。カードの表示や初期選択を同意としない。

Markdown・UI・PDFは同じ確定結果から生成する。完成文書の表示に元run一式や最新計算エンジンを要求しない。PDFは標準成果物。証明取得前後を区別し、Markdownへの署名をPDF自体の署名と説明しない。PDFに元文書の証明番号・検証方法を載せてよい。

MCPへの検証送信とWeb表示への送信は、項目・目的・送信先を示して明示同意を得る。両方を明示した一括確認は可能だが、一方から他方の同意を推定しない。同意前に文書・モデル・見積由来の照合情報を外部登録しない。

失敗時も成果物を保持し、同じ内容の再送だけなら再解析・重複同意を要求しない。内容変更は版更新と必要な再検証・同意を行う。

## 7. Web表示

Markdownと任意の証明データをPOSTで受け、HTMLを返す。保存・ログイン・受付・ポーリング・MCP再計算なしで表示可能とする。URLだけでは後日同じ文書を復元できないことを示す。

信頼する発行元の鍵で署名と文書一致を検証する。文書が提示した鍵を自己申告だけで信頼しない。署名確認、文書一致、オンライン失効照会を別状態とする。失効照会不能は未確認と表示し、文書表示自体を常時MCP接続に依存させない。未証明・無効を証明済みと表示しない。

危険なHTML・スクリプトを実行せず安全に整形する。保存なしでは本文をDB・ストレージ・ログ・監視へ残さず、キャッシュを抑止する。入力・処理量に上限を設ける。

ブラウザーへPOST結果を渡す経路は実ChatGPTで検証する。サーバー応答の成功だけで利用者への表示成功としない。

## 8. 任意の保存と本人確認

基本の証明発行に利用者ログインを必須としない。この場合は提出者本人性を証明しない。発行元の署名と利用者認証を区別する。

保存を選んだ場合だけ本人確認し、期間・閲覧範囲・延長・削除を案内する。保存同意は証明取得・表示同意と別。本人限定と一般公開も別操作。30日等の保存方針を文書・証明の共通契約へ埋め込まない。

## 9. 検証と受入

MCPは固定入力でルール、算術、不整合拒否、署名、改変、再送を単体検証する。ローカルは範囲反映、不足判定、計算、媒体一致、同意前送信禁止、障害時保持を検証する。Webはサンプル文書・証明だけで整形、検証状態、安全化、保存なし動作を検証する。AIの意味解釈は代表ソースによる別評価とし、単体試験で保証しない。

契約試験には正常、旧版、未知版、不足、改変、無効署名、部分試算を含め、他の実サービスなしで実行できること。

- Web停止でもローカル文書・PDFを利用できる。
- OAuth未設定・DB未接続でも保存なしWeb表示が動く。
- MCP停止でも完成文書を表示でき、鍵があれば署名検証できる。
- 保存停止が表示を止めない。
- ルール更新後も過去文書を表示できる。
- 元runなしでも持ち出した文書・証明を利用できる。
- Web表示変更にプラグイン同時配布を要求しない。

実ChatGPTでカード、PDF、同意、証明取得、ブラウザー表示を通す。模擬ホスト試験を実ホスト受入と呼ばない。

## 10. 移行と完了状態

旧URL・保存結果の互換処理は隔離し、新基本経路の前提にしない。不要なAPI・状態・UI・設定・コード・テストは新経路受入後に整理する。既存文書・証明の検証可能性は保持する。

「見積作成済み」「証明取得済み」「Web表示済み」「保存済み」を独立して報告し、一方から他方の完了を推定しない。Web表示・保存は証明付き文書の利用方法を拡張する機能である。
