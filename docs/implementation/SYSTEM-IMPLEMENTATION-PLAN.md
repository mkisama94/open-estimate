# Open Estimate 一括同意とWeb保存の実装指示書

更新日：2026-10-28。基準実装：0.11.1。上位仕様：[SYSTEM-SPEC.md](SYSTEM-SPEC.md)。設計背景・画面文言：[WEB-PUBLICATION-SIMPLIFICATION-PROPOSAL.md](WEB-PUBLICATION-SIMPLIFICATION-PROPOSAL.md)。

本書の新設ファイル・ツール・API・コマンドは実装対象であり、既に利用できるものではない。旧版の「Markdown必須・保存なしPOST・工程別同意」の実装指示を本書で置き換える。過去の受入記録を新仕様の合格記録に読み替えない。

## 1 実装の目的と完了条件

次の標準フローを実装する。

```text
本文を読まない構成確認
  → 対象と全工程を提示し、読取・検証・公開を一画面で選んで開始
  → 取得・解析・算定
  → 結果カードとPDFを表示
  → 選択済みならMCP検証・証明取得
  → 選択済みならWeb保存
  → 結果URLと公開終了日を返す
```

全工程を選んだ正常系では、開始後の製品側追加同意を0回にする。ブラウザーでファイルを選ばせず、返されたHTTPSリンクを開くだけで保存済み結果を読めるようにする。Web公開は365日、ダウンロード済みPDFは期限後も利用可能とする。

MCPは数値検証と証明、Webは保存と表示、ローカルは対話と処理の進行を担当する。MCPからWeb登録を呼ばない。実装依頼時は、細かいマイルストーンを検証単位として使い、ローカル部品だけで完了とせず実ホストでの全工程受入まで進める。必要な外部接続が得られない場合は、その未達を具体的に記録する。

本人限定の新規保存、課金、アカウント別一覧、共同編集、公開結果検索、自由記述の公開、測定ルール・係数の変更は今回の対象外とする。

## 2 着手時の確認と優先順位

1. 作業ツリー・配布版・現行ツール・環境設定を確認し、利用者の変更を保持する。0.11.1の再同意修正と既存取得改善を退行させない。
2. 本書・SYSTEM-SPEC.mdを優先し、旧運用文書やSkillの「毎回確認」「保存なし」「ファイル選択」を新実装の要件として採用しない。
3. 下記の契約の最小形と合成データを用意し、実ホストの開始画面から証明・Web登録・URL表示までを早期に通す。UIの承認イベントがローカルへ渡り、算定後の送信へ適用されるところまで確認する。
4. 本番データや利用者のソースを境界試験に使わず、テスト鍵・専用のステージングDBを使う。

実ホストが新ツールを読み込んでいなければ、更新・再接続の手順と必要な作業を特定する。模擬ブリッジで成功したことを代替の完了証拠にしない。

## 4 契約を先に固定する

### 4.1 構造化結果

`oes/estimate-result/v1` を新しい正本とする。既存EstimateDocumentの結果・為替・品質を再利用できるが、Markdownテンプレートや元runを必須フィールドにしない。

結果には測定日時、TEST区分、工数のp25/中央値/p75、人日基準、金額・通貨、機能規模、取得充足、全体／部分、暫定・未確認件数、規定理由コード、ルール・係数版、固定した為替条件を含める。案件名・機能名・パス・任意URL・自由記述は禁止し、`additionalProperties: false` 相当で未知項目を拒否する。表示文言はコードから生成する。

小数・日時・単位・丸め・nullの意味を固定する。既存の正規化JSON方式を使い、同じデータのキー順変更でハッシュが変わらないことを独立fixtureで確認する。Webの公開ID・公開期限・管理秘密はEstimateResultに混ぜない。

カード・本文・Markdown・PDF・Webはこの確定データだけから生成する。表示やPDF再生成でルール・為替を取り直さない。署名・公開の関数はオブジェクトを受け取り、MarkdownやPDFの未作成状態でも動作させる。

### 4.2 検証と証明

`oes/estimate-proof-request/v1` は `operation_id`、`result`、`validation_input` を持つ。validation_inputは匿名の数値モデル、配布整合性情報、ルール参照、必要な計算照合情報に限定する。詳細モデルの機能IDは名称から作らず、無意味なIDに変換する。

MCPツール名を `issue_estimate_proof` とする。形式・ルール・数値モデル・計算条件・結果との一致を検証し、成功時だけ `oes/estimate-proof/v1` を返す。署名文には方式識別子、発行元・環境、証明番号、発行日時、結果ハッシュ、ルール参照、検証範囲・制約、鍵ID・方式を含める。旧 `oes/document-proof/v1` とは別のドメインとして署名する。

`src/core/numeric-model.ts`、正規化、`src/issuer/signing.ts` 等の純粋な処理を再利用する。旧 `assertDocumentMarkdown` や文書本文一致を新経路の検証条件にしない。未知ルールや計算不一致は失敗させ、結果をサーバー側で黙って修正しない。

発行記録は操作ID・要求指紋・証明・発行時刻に限定し、モデルや結果本文を保存しない。旧表を変更して新旧証明を混同せず、新方式の表または方式を明確に分離したリポジトリを使う。原子的な保存と同一操作の再送保証を維持する。署名後・記録前の障害では成功を返さない。

### 4.3 Web API

| API | 入力と挙動 |
|---|---|
| `POST /api/results` | JSONの `operation_id`、`result`、`proof`、`withdrawal_token_hash`。保存後にURL・ハッシュ・公開日時・終了日時を返す |
| `GET /results/{id}` | 保存結果をHTML表示。正常200、未知404、期限終了・停止410。終了状態に本文を含めない |
| `GET /results/{id}/pdf` | 同じ結果・証明からPDF取得。期限・停止検査はHTMLと共通 |
| `GET /api/result-operations/{operation_id}` | 管理秘密をAuthorizationヘッダーで渡す読取専用照会。登録状態・URL・期限だけを返す。未登録404、秘密不一致は情報を返さない |
| `POST /api/results/{id}/withdraw` | 管理秘密をAuthorizationヘッダーで渡して公開停止。URLやCookieに秘密を入れない |

登録応答は `schema_version`、`status`、`public_result_id`、`canonical_url`、`result_hash`、`published_at`、`expires_at` を持つ。新規201、同一再送200、異なる要求の同一ID409、形式不正400、上限超過413、証明不一致422、制限429、サービス障害503を基準とする。停止・期限終了の再送は410と状態を返し、成功時の本文を再送しない。

入力上限は既存数値モデル・文書の正常最大fixtureを測って設定する。文字列長・配列数・深さ・受信総量を制限し、未知フィールドを拒否する。任意のHTML・画像・埋込URLは受け入れない。

## 5 開始時の一括同意を実装する

### 5.1 開始画面と操作

ローカルMCPに `show_estimate_start` と `start_estimate_workflow` を追加する。前者は本文を読まずに作成した対象・範囲・上限・送信方針を表示し、後者は明示操作で選択した設定を保存する。新設名はCLIとも意味をそろえる。

チェック項目は初期未選択の「読取・解析」「検証・証明」「1年間のWeb保存公開」。ボタンは「選択した内容で見積を開始する」。読取は必須、公開には検証が必要で、依存違反を同じ画面で解決する。未選択項目を自動承認しない。本文で代替する際も三つの組合せを一度で確認する。

送信先の実URL、MCPだけに送るデータ、公開するデータ、送らない機密、365日公開、品質区分・部分試算の扱いを示す。数値は後から確定すると説明する。モデル提供元の補足文言はSYSTEM-SPEC.mdの表現を使う。

### 5.2 承認条件と実要求を分ける

`WorkflowConsent` にはworkflow_id、対象候補・取得計画へのローカル参照とハッシュ、選択した操作、契約版、送信先・環境、計算方針・通貨・ルール、公開期間365日、品質の扱い、明示操作の証跡、承認日時、取消状態を保持する。まだ存在しない結果ハッシュを初回承認の入力に要求しない。

算定後、`authorizeRequest(consent, request, stage)` 相当の純粋関数で承認条件と照合し、要求ハッシュ・段階・操作IDを承認へ結び付けた適用記録を作る。これは追加同意ではない。外部送信直前にも取消と条件を検査する。表示のbooleanだけで自由な要求を許可しない。

UIの明示操作またはホストが報告した実回答を証跡にする。サーバー側で本人性を証明したとは扱わない。開始画面を表示しただけで開始しない。ホストの独自確認は回避せず、製品側の同意と別に測定する。

### 5.3 再確認を求める条件

範囲内での算定値確定、宣言済み品質判定、分割取得、証明番号・URLの発行、同一要求の再試行は追加確認しない。対象外の読取、送信項目・先・目的・計算方針の変更、未選択工程の追加だけを差分確認する。機密混入や不正署名は同意で迂回せず修正する。

`src/mcp/server.ts` の `confirm_workspace`、`authorize_partial`、`src/local/cli.ts` の確認・部分試算許可と取得経路を調査する。承認済み対象の読取や事前説明済みの部分試算に、別のユーザー回答を要求しない接続へ変更する。対象・範囲検査は残し、既存フラグを無条件trueにする修正は禁止する。

Skill、ツール説明、CLI contract、カードの文言を同時に改修する。新経路に「実要求全体への新しい明示回答が必須」という旧前提を残さない。旧ツールを互換として残す場合は、新経路から呼ばない。

## 6 ローカルの進行処理と復旧

AIによるソース解釈は既存ホストが担い、Skillが承認済み作業を継続する。すべてを単一の長時間ツールへ押し込めない。解析結果の受取後は、`complete_estimate_workflow` 相当のローカル操作に構造化結果と検証入力を渡し、承認条件検査・固定・表示・必要なネットワーク処理を進める。

MCPへの通信は通常のJSONパラメーターとし、接続アダプターでプロトコルを処理する。Web登録もJSONで行う。ローカル状態への自動保存は許容するが、利用者がファイルを選択・開くことや、公開処理がMarkdownから数値を読み戻すことを要求しない。

最小の状態は、承認と取消、確定結果、PDF状態、証明状態、公開状態、最後のエラーとする。サーバー受付を別に作ったり、進捗ポーリングを追加したりしない。公開状態は未実行・完了・再試行待ち・停止・期限終了を識別できればよい。

proof_operation_id、publish_operation_id、公開停止用秘密を送信前に生成し、要求と共に再開可能なローカル状態へ保存する。秘密はモデル向け結果・通常ログ・共有ファイルに出さず、ホスト非公開状態または制限したローカル領域で管理する。保存不能なら復旧可能と報告せず、未公開のまま理由を返す。

通信アダプターを差し替え可能にし、ネットワーク不要の単体試験を用意する。通信中の結果不明は同一要求の再送で確かめる。新IDを発行してやり直さない。429/通信障害は有限回の再試行、形式・署名不正は再試行しない。証明取得済みならWeb登録だけ再開し、既存の数値・係数・為替を更新しない。

返却証明の結果ハッシュ・発行元・方式・環境を確認し、Web応答の結果ハッシュ・公開ID・URL・日時も確認する。URLは環境設定の許可されたHTTPSオリジンと結果ルートに限定する。任意の返却URLを無検査でリンクにしない。

取消は未実行の後続処理を止める。取消後は登録POSTの再送をしない。通信中に公開が確定した可能性があれば元の応答または読取専用の操作照会で確かめ、完了分を報告して公開停止操作を案内する。実行中要求の最終状態が不明なら「取消済み・公開なし」と断定しない。照会は異常時の復旧用とし、正常系の進捗ポーリングには使わない。

## 7 Web保存と365日の期限

### 7.1 保存の最小構成

新しい公開結果テーブルを追加する。概念上の項目は、公開ID、operation_idの一意制約、要求指紋、result_hash、result_json、proof_json、withdrawal_token_hash、published_at、expires_at、状態、停止日時。本文は期限削除後にnull等へできる設計にする。期限検索用インデックスを設ける。

次の未使用番号で追加マイグレーションを作る。既存の0001〜0008を書き換えない。新公開テーブルだけのDBで登録・表示・停止・期限試験を実行できるようにする。旧所有者・ブラウザーセッション・転送受付への外部キーを設けない。

登録はスキーマ・信頼鍵・署名・結果一致・本番環境を検査してから、結果と冪等情報を原子的に保存する。要求指紋には結果・証明・管理秘密のハッシュ等、意味のある入力全体を含める。ランダム公開IDは対象名や連番から生成しない。結果データから公開IDを再計算して管理権限にしない。

並行登録の一意制約競合は、確定済み行を読み直して要求指紋を比較する。同一なら元のURL・日時、異なるなら409を返す。保存に失敗した場合はURL成功応答を返さない。

### 7.2 期限と公開停止

サーバー時刻で最初の保存確定時に `expires_at = published_at + 365 * 24 * 60 * 60 * 1000` を設定する。日付文字列の翌年置換は使わない。Web表示には明確な公開終了日を示す。再送・閲覧で時刻を更新しない。

HTML・PDF・データ出力の全経路で `now >= expires_at` と停止状態を検査する。期限・停止後は本文を返さず410と説明だけを返す。通常ページ・PDF・終了応答にはno-store等を設定し、CDNの古い本文で期限や停止を迂回できないようにする。

定期処理で期限切れ本文と証明本文を削除する。1回の件数を制限し、再実行可能にする。公開ID・操作ID・要求指紋・状態・日時等の最小記録は残し、古い操作の再送で再公開されないようにする。削除処理の停止が閲覧期限を延ばさないことを必須とする。

公開停止用秘密は十分な乱数（32バイト以上）でローカル生成し、Webはそのハッシュとの一致で認可する。比較・試行回数制限を実装し、状態変更をGETで行わない。公開URLやCookieの所持を管理権限にしない。停止操作は再送可能とする。

公開期限はMCP証明の失効期限ではない。公開期限後もローカルPDFはオフラインで読め、旧証明の検証鍵を削除しない。PDFにURLを載せる場合は公開終了日を併記する。自動延長・自動再公開・延長承認待ちは追加しない。

### 7.3 入口と設定

新規ルートを `src/web/worker.ts` の旧OAuth・Cookie・Origin・owner-previewの共通判定より前に振り分ける。旧ルートのCSRF保護は変更しない。新APIはCookie認証を使わず、公開停止は管理秘密を明示して認可する。ブラウザーに不要なCORS許可を追加しない。

Webの必要設定は専用DBバインディング（例PUBLIC_RESULTS_DB）、許可する環境と発行元、信頼済み公開鍵、入力・登録制限。新規登録停止スイッチを設ける場合も既存結果の読取を停止させない。DBの物理共用は許容するが、新旧テーブルと移行・削除処理は分離する。

MCPの発行鍵・発行記録とWebの結果DBを互いの起動条件にしない。365日は本契約の定数とし、承認時と登録時で異なる任意環境値を使わない。Workerのログ・監視に検証モデルや管理秘密を出力しない。

## 8 結果カードとPDF

結果カードの最上部は総工数の中央値を大きく表示し、人日・参考幅・TEST・品質を続ける。未取得の主要ソースがある場合は「全体工数：未算出」が主表示で、部分の値を別に出す。詳細は人が読める表・説明で表示し、生JSONだけにしない。

承認済み工程の進行中に「送信してよいですか」「公開してよいですか」を表示しない。公開完了後は結果URL・公開終了日・PDFを提示する。未公開の選択なら選んだ工程までで終了し、追加の公開を押し付けない。

PDFは固定データから生成し、証明番号・保証範囲を付記する。PDF自体の署名とは区別する。PDF生成障害でも結果を失わず、その生成だけ再試行する。全体・部分・長い数値・日本語のサンプルを全ページ描画して確認する。

「一時表示」「30日保存」「延長」「本人限定」「ファイルを選択」「確認コード」の旧UIを新カードから削除する。公開停止は所有者側の管理操作に置き、一般閲覧画面に認可なしの停止ボタンを置かない。

## 12 配備と切替

1. 新契約・テスト・追加マイグレーションを準備し、ステージング用の鍵とDBを設定する。秘密鍵をチャットやGitへ出さない。

3. 本番とステージングでサービス設定・信頼鍵・署名環境を整合させる。Webの保存先をMCPと取り違えない。
4. 新しいローカル配布物を別ディレクトリーへ移して起動・カード・PDF・新ツール宣言を確認し、実ホストへ読み込んでM5を実施する。

ロールバックは新規発行・登録を停止できるようにし、既存公開結果の期限付き閲覧・公開停止、旧データ、検証鍵を保持する。ソフトウェアの切戻しで365日結果を15分・30日の削除処理へ流さない。
