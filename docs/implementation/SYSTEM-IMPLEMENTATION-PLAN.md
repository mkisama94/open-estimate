# Open Estimate 新システム実装指示書

作成日：2026-10-28（JST）  
上位仕様：[システム仕様](SYSTEM-SPEC.md)  
基準：現行0.10.0のコードを調査した実装計画。以下の新設API・ファイル・コマンドは実装予定であり、存在や動作を保証する記述ではない。

## 1. 実装の目的と完了条件

MCPはルール配信・検証・証明発行、ChatGPTローカルは対話・取得・解析・算定・文書生成、Webは受信文書の表示を担う構成へ移行する。中核成果物を、Web保存レコードから、持ち運べるMarkdownと証明データに変更する。

完成条件は、実ChatGPTで対象同意から算定、Markdown・PDFの取得、検証送信への同意、MCPの証明受領、ブラウザーでの保存なし表示まで通り、各処理系の停止が他の独立機能を止めないこと。各マイルストーンの完了だけで全体完了としない。

### 今回の範囲

- 独立した文書・検証・証明・表示の契約と実装。
- ローカル成果物、Intelligent UI、PDF、同意・再送処理の改修。
- ログイン不要の文書証明発行と、保存なしPOSTプレビュー。
- 取得範囲・充足判定の既存改善を維持し、新しい出力へ正しく接続する。
- 旧仕様との互換境界、不要コード削減、個別ビルド・契約テスト・障害分離試験。

### 今回拡張しないもの

新しい本人用保存機能、課金、一般公開、提出者本人の証明、ソースの独立監査は追加しない。既存の保存・ログイン・旧証明の閲覧経路は互換性維持の対象とし、新基本経路の前提から外す。測定ルール・係数をこの改修に便乗して変更しない。

## 2. 最初に検証する技術的な境界

大量の移植前に、合成文書とテスト鍵で以下を実証する。

1. 実ホスト内でローカルの結果カードとPDF取得を操作できる。
2. 利用者の明示操作から、ブラウザーへMarkdownをPOSTしてHTML応答を表示できる。
3. Web側にOAuth・保存DBがなく、MCPが停止していても2が成立する。
4. 署名付き文書を独立した公開鍵で検証でき、1文字改変を検出できる。

ブラウザーへの受渡しは、ホストが実際に提供する手段を調査して選ぶ。リンクを開く操作がPOST本文を受け取ると仮定しない。MCPツールがHTMLを受け取っただけでブラウザー表示成功としない。

ローカル中継を使う場合は、ローカル側の一時的な受渡しアダプターに限定し、寿命・接続元検査・本文非記録を定義する。Webサーバーへ事前保存して短期URLを作る方式を、保存なしの代替実装としない。本文をクエリ文字列やURL断片へ埋め込まない。

実ホストで自動受渡しができない場合は、ファイル選択等の代替と操作数を報告する。黙って旧受付・保存へ戻さず、当該受入を未達として管理する。他の独立モジュールの実装は進めてよいが、標準体験の成立を先送りしたまま完了報告しない。

## 3. モジュール境界

新設名は下表を基準とする。同等の責務を持つ既存ファイルへ整理する場合は、受入記録に対応表を残す。

| 配置案 | 責務 | 禁止する依存 |
|---|---|---|
| `src/contracts/document.ts` | 文書データ・検証依頼・証明・表示入力の型とスキーマ | local、remote、web、DB、環境変数 |
| `src/document/markdown.ts` | 標準Markdownの生成・構文検査・主要値の照合 | 計算エンジン、通信、認証 |
| `src/document/presentation.ts` | 確定データから表示項目への純粋変換 | 再計算、保存条件 |
| `src/proof/verify.ts` | ハッシュ・署名・発行元信頼のオフライン検証 | ネットワーク、DB、秘密鍵 |
| `src/issuer/service.ts` | ルール選択・数値検証・証明発行・再送処理 | Web UI、ブラウザーセッション、保存済み見積テーブル |
| `src/issuer/signing.ts` | 注入された発行鍵による署名 | Web画面、所有者認証 |
| `src/issuer/repository.ts` | 最小発行記録と競合制御 | 見積本文・モデルの永続保存、利用者向け履歴 |
| `src/local/document-result.ts` | runから持出し可能な成果物を生成 | Web内部URL形式、保存DB |

| `src/local/web-handoff.ts` | 同意済み文書のブラウザー受渡し | サーバーへの仮保存、元ソース送信 |

旧実装は互換アダプターからだけ参照する。最初から全ファイルを移動するより、新経路の依存グラフを先に閉じ、不要な呼出元を除去してから削除する。

## 4. 入出力契約を固定する

### 4.1 文書データ

`oes/estimate-document/v1` を定義する。最低限、文書形式版、テンプレート版、測定日、ルール参照、計算条件、取得充足、品質集計、機能規模、工数、金額・為替条件、注意事項を持つ。値の精度・丸め・未算出の扱いは既存の確定結果を保持する。

ソース、絶対パス、判断台帳、run ID、Webの受付・保存ID、30日保存条件、ログイン情報を公開可能な文書データへ入れない。元runへの関連付けと詳しい根拠はローカル専用の別ファイルへ置く。

標準成果物を `estimate.md`、`document.json`、`estimate.pdf`、証明取得後の `proof.json` とする。`estimate.md` と `proof.json` だけで表示・署名検証可能にする。再計算に使う数値モデルは別の検証入力に置き、Webへ送らない。

### 4.2 Markdownと数値の一致

文書確定時にUTF-8・BOMなし・LF・末尾改行1個へ正規化し、それ以後のバイト列を固定する。発行・検証時は暗黙の再正規化をせず、不正な形式は文書再作成へ戻す。Markdownへ証明番号を後から追記して署名対象を変えない。証明番号は外側のUI・付属証明・PDFの案内欄へ表示する。

主要数値・単位・ルール版・品質・全体／部分は版付き標準テンプレートから決定的に生成する。MCPは提出されたdocument.jsonと検証入力を照合し、その版のテンプレートを再生成して主要領域の完全一致を確認する。任意のMarkdownから正規表現で数値を拾う方式にしない。

自由記述を許す領域はテンプレートで区分し、見出しや数値領域の重複・差込みを拒否する。自由記述の意味の正しさは証明しない。文書全体はハッシュに含める。文書のハッシュだけを署名した結果を「数値検証済み」にしない。

PDF・UIは同じ確定データを使う。PDFを再生成する際に係数・為替を取得し直さない。テンプレートの旧版を読める読取機能を維持し、最新ルールとの差を理由に過去文書の表示を拒否しない。

### 4.3 検証依頼

`oes/document-proof-request/v1`：ランダムな操作ID、ルール・計算条件の参照、数値モデル、document.json、確定Markdownを持つ。本文サイズ・項目数・深さを制限し、未知フィールドを拒否する。MCPへ渡す前にローカルで送信対象の実物を示す。

送信同意はローカルに、送信先・目的・要求全体のハッシュ・日時・明示回答の記録として保持する。自己申告のbooleanだけをサーバー側の本人証明と扱わない。秘密鍵や認証トークンをAIの引数・チャットへ渡さない。

### 4.4 証明

`oes/document-proof/v1`：発行元、証明番号、発行日時、文書SHA-256、ルール版、検証方式・範囲・制約、鍵ID、アルゴリズム、環境区分、署名を定義する。署名対象には方式識別子を含め、旧証明と取り違えない。

既存のEd25519と正規化JSONの実装・テストを再利用する。署名対象のスキーマとバイト列を固定し、独自の暗号方式を作らない。鍵の選択は信頼済みカタログから行い、入力された任意URLや埋込公開鍵を信頼しない。

文書形式検査、主要数値の整合、規則版の検査、署名対象文書との一致を証明範囲に含める。ソース網羅性・AI意味判断・為替データの真正性・実工数・提出者本人性は独立監査していない旨を含める。取得充足はクライアント申告であり、COMPLETEでもサーバーがソースを検査したと表示しない。

`DOCUMENT_REGISTERED` と `CALCULATION_VERIFIED` の意味を契約上分ける。初期実装は後者を提供し、検証失敗時に前者へ黙って降格して発行しない。文書登録のみの新APIは今回追加しない。

### 4.5 検証状態

署名VALID/INVALID/UNKNOWN_KEY、文書MATCH/MISMATCH、発行元TRUSTED/UNTRUSTED、現在状態NOT_CHECKED/ACTIVE/REVOKED/UNKNOWNを別々に返す。署名有効と現在も有効を混同しない。Webは表示・検証に数値モデルや測定ルール全文を要求しない。

## 5. MCP・証明発行の実装

### 残す・再利用するもの

- `src/remote/measurement-rules.ts` と `src/rules/measurement-contract.ts` の版付きルール取得・固定。
- `src/core/numeric-model.ts`、計算処理、品質検査の必要部分。
- `src/core/canonical-json.ts`、`src/web/signing.ts`、`src/core/certificate-verify.ts` の暗号・正規化・検証の純粋な部分。新しい証明型へ分離し、既存型との互換性を壊さない。

### 新しい入口

`issue_document_proof` をremote MCPへ追加する。入力検査 → 対応ルール・計算基準の選択 → 数値検証 → 文書一致検査 → 署名 → 発行記録確定 → 証明返却を一つの要求で行う。掲載URLや所有者IDを返さない。

ツールは書込・外部送信を伴う操作として宣言する。一般利用者のOAuthを要求せず、入力上限、全体のレート制限・発行容量制限を設ける。`get_measurement_rules`等の読取を、署名鍵や発行DBの準備不足で停止させない。

`publish_estimate`・Web利用可否・進捗表示をMCPの基本機能から外す。移行期間に残す場合は互換用と明示し、新しいSkillから呼ばない。

### 最小発行記録

新しい記録は操作ID、要求指紋、証明番号、署名済み証明、発行日時・状態を保持する。Markdown・数値モデル・対象名・ログイン情報は保存しない。既存の見積保存テーブル・承認受付・所有者セッションを参照しない。物理DBを共用しても、新テーブルの準備だけで発行を試験できること。

同一ID・同一要求の再送は保存された同じ証明を返す。並行要求では確定した一件だけを返す。同一ID・異なる要求は競合として拒否する。記録確定前に発行成功を返さない。既存Webの30日削除処理へ発行記録を混ぜない。

初期実装では最小発行記録を自動失効・自動削除しない。将来保持期限を設ける場合は、再送保証期間と削除後の挙動を別の契約改訂で定義する。文書本文は処理終了後に保持せず、ログにも残さない。

### 鍵と失効

署名秘密鍵は発行Workerのsecretだけに置く。ローカル・Web表示・配布物・Gitへ含めない。テスト鍵と本番鍵は識別子・環境・信頼カタログで分離する。Web用鍵一覧は運用者が信頼する経路で配布し、毎表示でのMCP接続を不要にする。

鍵更新で旧文書が表示不能にならないよう、旧検証鍵を維持する。新発行停止と過去署名の検証を分離する。オンライン失効照会は任意の補助機能とし、初期未提供なら常にNOT_CHECKEDと表示する。未実装の失効確認をACTIVEとして返さない。既存旧証明の失効機能は維持する。

`src/local/estimate-result.ts` を、文書生成、表示、送信同意、ネットワーク処理へ分ける。`readRun`は文書生成時の検査に使い、完成文書の再表示では呼ばない。`src/core/estimate-publication.ts`に集まっている表示・計算検査・保存条件を分離する。

| `show-document` | 文書パス → UI用データ | なし |
| `render-document-pdf` | 固定文書 → PDF | なし |
| `prepare-proof-request` | 文書・検証モデル → 送信内容と要求ハッシュ | なし |
| `consent-document-action` | 文書版・送信先・目的・明示回答 → ローカル同意記録 | なし |
| `proof-request-input` | 同意済み操作 → 同じ要求 | なし |

名称は実装時に既存互換名を設けてよいが、意味の違う旧publicationコマンドを同じ名前で動かし続けない。

証明受領時は要求した文書ハッシュ・ルール版・発行元・署名を確認し、取り違えた証明を添付しない。失敗時も元文書を残す。証明後PDFは証明番号・元文書ハッシュ・検証方法を添付情報として加える。PDF自体は未署名であることを区別する。

`src/local/result-widget.ts`、`src/local/estimate-ui.ts`、`src/local/estimate-pdf.ts`は純粋な文書表示へ接続する。「この結果の証明を取得」「Webで表示」「PDFを取得」を目的別にする。保存しない表示ボタンに「本人限定30日保存」の同意を混ぜない。

`skills/open-estimate-assessor/SKILL.md`、`src/local/cli.ts`のcontract、ローカルMCPの宣言からWEB_SAVEDを唯一の完了条件とする記述を削除する。表示成功・証明受領・保存を独立に記録する。HTML応答取得だけなら「表示用データ取得済み」、実表示未確認ならその旨を示す。

取得改善は`src/collector/acquisition-plan.ts`、`acquire.ts`、`coverage.ts`を再利用する。85 MiBの対象外資料・主要ソース・ネストしたrelease・複数バッチの回帰試験を維持し、scope_coverageを新文書へ引き継ぐ。

## 7. 保存なしWeb表示

新規の `POST /preview` を設ける案を基準とする。ブラウザーのフォームPOSTを受けられる形式で、Markdownと任意のproofだけを受信する。上限は復号後の本文長と受信総量の両方で検査する。未知の形式は400、過大入力は413とし、本文をエラーへ反射しない。

処理は入力検査 → 任意証明のオフライン検証 → Markdown安全化・整形 → HTML応答。リダイレクト後のGETで本文を復元するための一時保存は作らない。GETには文書選択等の入口説明だけを返し、URLだけでは見積を復元しない。

対応Markdown構文を限定し、生HTML、スクリプト、イベント属性、危険なURLを無効化する。外部画像・埋込み・追跡リソースを自動取得しない。証明バッジは本文から生成せず、検証結果からページ外枠に表示する。未証明の本文が「証明済み」と書いていても信頼表示と混同させない。

`Cache-Control: no-store`、適切なCSP、Referrer-Policy等を設定する。Cookieやログインセッションを読まない。通常のブラウザーPOSTにOriginがあることだけを理由に既存の掲載APIと同様に拒否しない。入力送信と表示の境界を新経路用に設計し、旧保存APIのCSRF保護は弱めない。

DB・OAuth・発行鍵を一切与えない環境でビルド・起動・試験する。処理に必要な公開鍵を渡すことは許容する。本文をconsole、監視イベント、例外情報、CDNキャッシュへ記録しない。プラットフォーム側のログ・キャッシュ設定も受入対象にする。

Cloudflareでは`wrangler.jsonc`のassetsより先に `/preview` を処理するルート設定を追加する。既存MCPルート・旧URL・保存画面と衝突させない。表示だけのリリースを発行DB移行やAuth0設定で停止させない。

## 9. 独立したビルド・設定

発行側はルールカタログ・発行鍵・発行記録・制限設定、ローカルはNode・文書/PDF資材、Web表示は整形器・信頼済み公開鍵だけで成立させる。Web保存用Auth0設定は保存互換に閉じる。

個別のテスト・ビルドコマンドを設け、全体版番号と契約互換性を混同しない。WebのCSS変更にスキルの新規登録を要求しない。リモート発行の受入済み契約に対して、ローカルの配布整合性検査は必要な範囲で維持する。

バンドル依存を検査し、Web表示に数値計算・秘密鍵コード・所有者認証・PDF生成処理を混入させない。新規の無効化スイッチは証明発行だけを止め、規則読取・文書表示を停止しない。環境不足はAUTH_CONFIGURATION_REQUIRED等に一括せず、担当機能の理由として返す。

## 11. 必須テスト

単体試験は固定入力・固定時刻・テスト鍵で決定的にする。実ネットワークは結合試験へ分ける。新規テスト名は例であり、対応する既存テストへ統合してよい。

| ID | 検証 | 主な配置案 |
|---|---|---|
| T01 | 文書のUTF-8、LF、改変、重複数値領域、旧テンプレート、未知形式 | `tests/unit/document.test.ts` |
| T02 | 署名、未知鍵、環境取り違え、異なる文書、証明範囲、失効未確認 | `tests/unit/document-proof.test.ts` |
| T03 | MCPの算術不一致、文書との不一致、同一再送、並行発行、記録失敗、発行停止 | `tests/integration/document-issuer.test.ts` |
| T04 | 元runを切り離した表示・PDF再生成、数値・条件不変、証明前後の区別 | `tests/integration/document-local.test.ts` |
| T05 | 同意拒否・未同意・要求変更・送信先変更・証明取り違え・応答消失復旧 | ローカル/MCP契約試験 |

署名ベクトルは署名者と検証者が同じバグで合格しないよう、独立した検証手段でも照合する。PDFは日本語・全体/部分・長い注意事項を含むサンプルを全ページ描画して確認する。AIの意味判断は別の評価セットで測り、暗号・算術試験の合格で保証しない。

実ホスト受入では「結果カード表示」「PDF取得」「同意」「証明取得」「ブラウザーでの表示」を個別に記録する。HTTP 200だけ、ローカル合成ブリッジだけ、URL発行だけで合格にしない。

## 12. 配備・移行・ロールバック

1. 契約・fixture・テスト鍵で独立試験を完了する。
2. ステージングで新発行記録だけを追加する。既存テーブルは破壊しない。
3. 署名鍵・信頼済み公開鍵を運用手順に従って設定し、テスト環境と分離する。
4. 新しいWeb表示とMCP証明を配備し、それぞれ単独で確認する。
5. 実ホスト用プラグインを更新し、M6を実施する。
6. 本番反映後、同じ合成fixtureで境界を確認する。実利用者データを無断で試験送信しない。

署名鍵設定、実ホスト接続権限、本番反映が未実施なら、その部分だけ未達と報告する。不要になった掲載用OAuth値を基本機能の残課題として要求しない。

ロールバックは新発行を停止しても既発行の検証鍵・記録・文書を保持する。旧保存サービスを巻き戻しても新しい持出し文書が消えないこと。旧証明と新証明を別方式として検証し、スキーマを上書きしない。
